# Physics playground

Open `Assets/Scenes/TrainPlayground.unity` and press Play. WASD moves, Shift runs with small alternating hops, and the mouse looks and aims both arms. Hold left or right mouse to grip with that hand; release to let go. Space jumps. Hold W while gripping a reachable ledge to pull up and lean over it. Escape frees the cursor and clicking the Game view captures it again.

The scene starts a local Netcode for GameObjects host. The server controls the capsule body, upright balance, movement, jump, jointed physics arms and legs, and spring grips. The continuous conductor mesh is skinned at runtime to the existing leg anchors; its importer needs Read/Write enabled. The server sends limb rotations to observers. Arm/torso collisions are enabled, with restricted shoulder joints. A released button, lost window focus or stale input clears the grip on the server. Hands can grip static geometry and server-owned, spawned network rigidbodies. The scene includes a server-authoritative test crate with NetworkRigidbody and NetworkTransform. Static train meshes use non-convex mesh colliders; a moving train needs suitable dynamic shapes and a separate network physics design.

During Play Mode, do not drag `Playground Player` underneath a terrain, hill, or other ordinary object in the Hierarchy: Netcode rejects and reverts that parent change. A networked parent must itself be a spawned `NetworkObject`, and only the authority may establish that relationship. Hill climbing should use the collision and movement systems, without reparenting the player.

This remains a physics prototype: skin weights are generated from position and require visual tuning; there are no individual finger or elbow joints. The grip attaches to an arm rigidbody at the hand position. On the server, each foot can form a temporary spring contact with walkable ground; stance alternates with the gait, releases on jump, and follows the velocity of an attached rigidbody. Leg swing starts from player input rather than waiting for velocity, while a planted leg drives toward its anchor. Ground movement depends on foot support; sprinting gives an upward impulse and alternates the leading leg between hops. Foot contact, foot sliding, acceleration, hop timing and joint stiffness still require gameplay and host/remote-client tuning, especially on moving trains and slopes. The local trial spawns a server-owned scene player for the host and an owned prefab for each connecting client. It uses direct loopback transport, not a lobby, Relay, reconnect or a finished session flow. Reconciliation, simultaneous grabs, late join, disconnect handling, latency and a moving train still need end-to-end tests before this can be treated as a complete multiplayer controller.

Ledge assist uses the existing hand springs and server physics. It checks for a steep static face, a walkable top and room for the torso. One hand can pull up by default; two hands give stronger assistance. Near the lip the body leans forward while the legs seek contact, then releases the ledge grip once the body is over it. Ordinary grips still work on eligible network rigidbodies, but climbing assist is for static level geometry. A high cliff needs reachable lips or intermediate ledges. Tune **Climb Acceleration**, **Climb Up Speed**, and **Climb Hands Required** on `PlaygroundPlayer` (scene player and remote player prefab).

Climbing Play Mode and host/client verification: **NOT RUN**. Try a low block first (look at the edge, hold one mouse button and W), then jump to a reachable cliff edge and try two hands. Release the grips midway once to check that the assistance stops.

On 2026-11-03 an editor-only host smoke probe moved the player in an empty area, requested a jump and created a temporary static wall at the left hand: movement, a 0.43 m jump and spring-joint creation all succeeded. The probe injected server-side intent and therefore did not validate mouse/keyboard input, release, dynamic targets or a remote peer. The wall and probe were temporary and did not change the saved scene.

On 2026-11-03 a Windows development client connected over loopback to the Editor host; both player objects appeared on the host. A development-only automated client sent movement and jump RPCs: its observed displacement was 3.10 m and its jump was 0.47 m. A separate host-side temporary probe confirmed that a hand attached to the spawned network crate and released it. The probe temporarily disabled crate gravity during acquisition; it did not validate carrying the crate, contention, crate replication on the client or mouse/keyboard input.

For a local two-process test, build using `Tools > Conductor Chaos > Build Local Trial Client`, start Play in the Editor, then launch `work/PlaygroundClient/ConductorChaos.exe -playground-client`. This is a development build and the trial uses loopback; it is not an online invitation flow.

Follow-up host probe on 2026-11-03 confirmed weighted legs, enabled arm/torso contacts, 2 mm maximum collider penetration during movement, 39.6 degrees of leg rotation, and grip release after an injected server RPC. It did not cover every pose or actual operating-system mouse input.

A separate development client connected to the Editor host and observed 2.93 m of movement, a 0.21 m jump and 17.2 degrees of replicated leg rotation. This automated input did not exercise a remote client's grip release or packet loss.
